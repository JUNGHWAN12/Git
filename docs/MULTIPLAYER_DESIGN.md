# 🌐 협업(온라인) 설계서
### 「커밋 크래프트」 교실 협업 모드 v1.0

> **결정: 협업은 게임의 핵심이므로 온라인(네트워크) 협업을 MVP에 넣는다.**
> 혼자 하는 NPC 모드는 없애지 않고 **"네트워크가 안 될 때·짝이 없을 때"의 대체 수단**으로 남긴다.

---

## 1. 왜 온라인이어야 하나, 그런데 왜 어렵지 않은가

**왜**: push 거절, pull 병합, 충돌, Pull Request 리뷰는 *다른 사람*이 있어야 의미가 생긴다. NPC는 각본대로만 움직이지만, 친구는 예상하지 못한 순간에 push하고, 같은 줄을 고치고, 리뷰에 이의를 단다. 그 경험이 협업 학습의 본체다.

**왜 어렵지 않나**: Git은 원래 **실시간 동기화를 하지 않는다.** 각자 자기 컴퓨터에서 작업하고, `push`·`fetch`·`pull`을 하는 순간에만 서버와 통신한다.
→ 이 게임의 온라인 기능은 일반 온라인 게임(위치·동작을 초당 수십 번 동기화)과 달리 **"버튼 누를 때만 주고받는" 단순한 요청·응답**이면 된다.

| 일반 온라인 게임 | 커밋 크래프트 |
|---|---|
| 초당 수십 번 상태 동기화 | `push`/`fetch`/PR 할 때만 통신 |
| 지연(렉)이 게임을 망침 | 0.5초 늦어도 문제없음 |
| 서버가 모든 상태를 관리 | 서버는 **허브 섬(원격 저장소)만** 관리, 각자 마을은 각자 PC에 |
| 연결이 끊기면 게임 중단 | 끊겨도 **커밋은 계속 가능** (push만 못 함 — 실제 Git과 같음) |

> 💡 **게임의 네트워크 구조 자체가 GitHub의 구조와 같다.** 서버 = GitHub, 학생 PC = 각자의 로컬 저장소. 구조가 곧 교재다.

```mermaid
flowchart LR
    subgraph 학생A PC
      A[내 마을<br/>로컬 저장소]
    end
    subgraph 학생B PC
      B[내 마을<br/>로컬 저장소]
    end
    subgraph 서버 = 허브 섬
      H[(팀 허브 저장소<br/>bare repo)]
    end
    A -- push / fetch --> H
    B -- push / fetch --> H
    H -. "알림: 단비가 push했어요" .-> A
```

## 2. 접속 방식 3가지 (같은 프로그램, 같은 규약)

| 방식 | 서버 위치 | 장점 | 단점 | 이런 학교에 |
|---|---|---|---|---|
| **A. 인터넷 서버** | 클라우드·교육청·학교 서버 (Godot 헤드리스) | 학교 방화벽 통과가 쉬움(`wss://`, 443 포트), 웹판도 접속 가능, 집에서도 이어서 가능 | 서버 운영 필요(소액), 개인정보 처리 검토 | 인터넷이 잘 되는 학교 |
| **B. 교실 서버** | 선생님 PC (게임의 "선생님 모드") | 인터넷 불필요, 데이터가 교실 밖으로 안 나감, 비용 0 | Windows 방화벽 허용 필요(관리자 권한), 교내망에서 PC끼리 통신이 막혀 있을 수 있음, 웹판은 접속 불가(exe 전용) | 인터넷이 막힌 학교 |
| **C. 혼자 모드 (NPC)** | 없음 | 언제나 동작 | 진짜 협업 아님 | 네트워크 실패·결석·자율학습 |

**자동 대체 규칙**
- 서버에 연결 못 하면 → "혼자 모드로 진행할까요?" (진도는 그대로 인정)
- 팀원이 3분 이상 응답이 없거나 나가면 → 그 역할을 **NPC 단비가 대신** (스테이지가 멈추지 않음)
- 연결이 끊기면 → 작업은 계속, `push`/`fetch` 시 "허브 섬과 연결이 끊겼어요" (실제 Git의 네트워크 오류와 같은 경험)

**P0에서 확인할 것** → `game/` P0 스파이크 **④ 교실 네트워크** 탭 (작성됨)
1. 선생님 PC에서 서버 열기가 되는가 (방화벽 창, 관리자 권한 필요 여부)
2. 학생 PC 3대 이상이 선생님 PC 주소로 접속되는가
3. (가능하면) 인터넷 서버 주소로 접속되는가
→ 결과에 따라 학교별 기본 방식을 A 또는 B로 정한다.

## 3. 방과 팀

| 개념 | 설명 |
|---|---|
| **방(교실)** | 선생님이 만든다. 6자리 방 코드 (예: `K7Q-M2X`). 학생은 방 코드 + 닉네임으로 입장, **선생님 승인 후** 참여 |
| **팀** | 2~4명. 선생님이 자동/수동 편성. 팀마다 **허브 저장소 1개** |
| **역할 카드** | 스테이지마다 배정: 🏗️ 건축가A / 🏗️ 건축가B / 🔍 리뷰어 / 👑 메인테이너(main 병합 담당). 스테이지가 바뀔 때 순환 |
| **학급 허브** | 이벤트용: 반 전체가 하나의 "학급 도시" 저장소에 PR (챕터 6 이후) |

### 3.1 수업 흐름 (선생님 화면)
1. 선생님 모드 실행 → 서버 시작 → **방 코드와 접속 주소**를 크게 표시 (프로젝터용)
2. 학생 입장 → 대기실 명단 → 승인 → 팀 편성 (자동: 출석 순서대로 2인 1팀)
3. 스테이지 시작 신호 → 모든 팀에 같은 스테이지 배포
4. **진행 현황판**: 팀별 허브 그래프·클리어 여부·막힌 팀 표시
5. 마무리: 프로젝터로 한 팀의 그래프를 띄워 함께 해석 ("여기서 왜 병합 커밋이 생겼을까?")
6. 수업 종료 → 진도 요약을 선생님 PC에 CSV로 저장 → 서버 데이터 삭제

## 4. 협업 스테이지 (챕터 5 협업판)

> 판정은 원래처럼 **최종 상태**로 한다 ([스테이지 명세 0.3](STAGE_SPEC_MVP.md)). 각 학생의 목표 = 자기 로컬 저장소 상태 + 팀 허브 상태.
> 협업판은 **혼자판의 NPC 행동을 실제 팀원 행동으로 바꾼 것**이다. 팀원이 없으면 원래 NPC 각본이 그대로 돈다.

| 스테이지 | 혼자판 (NPC) | 협업판 (2인 팀) |
|---|---|---|
| 5-2 섬 복제 | 단비의 허브를 clone | **두 사람이 같은 팀 허브를 각자 clone** → 같은 마을이 두 PC에 생김 |
| 5-3 비행선 출발 | 커밋 후 "단비가 볼 수 있나?" 퀴즈 | A가 커밋 → **B 화면의 허브 섬에 안 보임을 직접 확인** → A push → B의 허브 화면에 나타남 (B의 마을엔 아직 없음!) |
| 5-4 망원경과 우편함 | 단비가 push, 플레이어 fetch | A가 push → B가 `fetch` → B의 `origin/main`만 움직이고 마을은 그대로 |
| 5-5 우편함 열기 | merge origin/main, pull | B가 merge / pull로 A의 건물을 받음, 역할 바꿔 반복 |
| 5-6 착륙 거부! | 각본으로 거절 재현 | **두 사람에게 각자 다른 건물을 짓고 "지금 바로 push" 지시** → 늦은 사람은 반드시 `rejected` (서버가 보장, 4.1) → pull 후 push |
| 5-7 연결선 | 혼자 진행 | 혼자 진행 (협업 불필요) |
| 5-B 두 섬의 경주 | 각본 충돌 | 두 사람에게 **같은 분수 장식**을 서로 다르게 바꾸라는 비밀 미션 → 충돌 → 화면 아래 프리셋 대화("꽃이랑 등불 둘 다 하자")로 합의 → 해결 |

### 4.1 "착륙 거부"는 서버가 보장한다
- 서버의 push 처리 = 실제 Git 서버와 같은 **"기대값 비교 후 교체"**:
  학생이 보낸 `old`(내가 알고 있던 허브 main) ≠ 현재 허브 main → **거절**
- 두 명이 동시에 눌러도 서버는 한 번에 하나씩 처리하므로 **먼저 도착한 한 명만 성공**, 다른 사람은 실제 Git과 같은 `! [rejected] (fetch first)` 메시지를 받는다.

### 4.2 챕터 6 (PR·리뷰) — 2차 범위, 온라인 전제
- Pull Request, 코드 리뷰, 승인/변경 요청은 **진짜 사람끼리 해야 의미가 있다** → 2차에서 온라인 모드를 전제로 설계.
- 리뷰 코멘트는 프리셋 문장 + 금칙어 필터를 거친 짧은 자유 입력.

## 5. 통신 규약

- 전송: **WebSocket**, 메시지 = JSON 1개 (`"t"` = 종류). 교실 서버 `ws://<선생님PC>:8910`, 인터넷 서버 `wss://<주소>`.
- Godot 고수준 멀티플레이(RPC·동기화)는 쓰지 않는다: 실시간 동기화가 필요 없고, exe·웹판 공통의 단순 JSON이 디버깅과 학교망 문제 진단에 쉽다.
- 서버는 같은 Godot 프로젝트를 **헤드리스로 실행**한다 → 허브 판정(push 거절 등)에 클라이언트와 **같은 Git 코어 코드**를 쓴다.

| 방향 | 메시지 | 내용 | 상태 |
|---|---|---|---|
| → 서버 | `hello` | 버전, 닉네임, 방 코드 | ✅ 스파이크 |
| ← | `welcome` / `error` | 내 id, 명단 / 버전 불일치 등 | ✅ |
| ← | `joined` / `left` | 명단 변경 | ✅ |
| → / ← | `say` / `said` | 프리셋 알림 문장 | ✅ (시험판은 짧은 문장) |
| → | `fetch` | 팀 허브 id, 내가 가진 커밋 목록 | P1.5 |
| ← | `pack` | 내가 없는 객체(커밋·파일), 허브 브랜치 위치 | P1.5 |
| → | `push` | 브랜치별 `{old, new}`, 새 객체 | P1.5 |
| ← | `push_result` | 성공 / `rejected: fetch-first \| non-fast-forward` | P1.5 |
| ← | `activity` | "단비가 main에 push했어요" (**알림만**, 내 저장소는 fetch 전까지 그대로) | P1.5 |
| → / ← | `teacher_*` | 방 잠금, 승인, 팀 편성, 스테이지 시작·초기화, 현황 조회 | P3 |
| → / ← | `pr_*` | PR 생성·리뷰·병합 | 2차 |

**크기·빈도 제한**: 메시지 256KB, 학생당 초당 5개. 저장소가 작아(커밋 수십 개, 텍스트 파일 수십 개) 충분하다.

## 6. 안전·개인정보

| 항목 | 규칙 |
|---|---|
| 계정 | **없음.** 닉네임(12자 이내)만. 실명·학번 입력란 없음 |
| 입장 | 방 코드 + 선생님 승인 |
| 데이터 보관 | 서버는 **수업 중에만** 메모리에 보관, 수업 종료 시 삭제. 진도 요약 CSV만 선생님 PC에 저장 |
| 대화 | 프리셋 문장 기본. 커밋 메시지·PR 코멘트는 금칙어 필터 |
| 방해 행위 | `push --force`, 남의 브랜치 삭제는 **서버에서 거절**. 반복 방해 시 선생님이 퇴장 |
| 인터넷 서버(A) | 학교 개인정보 지침 확인, 접속 기록 최소화, TLS(`wss://`) 필수 |

## 7. Godot 구현

| 파일 | 역할 | 상태 |
|---|---|---|
| `game/core/net/protocol.gd` | 메시지 인코딩·검증, 버전, 포트, 크기 제한, 닉네임 정리 | ✅ |
| `game/core/net/room_server.gd` | WebSocket 서버(`TCPServer` + `WebSocketPeer`), 명단, 알림 전달 | ✅ 기본 |
| `game/core/net/room_client.gd` | 접속, hello, 받은 메시지함 | ✅ 기본 |
| `game/tests/test_net_loopback.gd` | 서버 1 + 학생 2를 한 프로세스에서 실제 통신 | ✅ CI |
| `game/scenes/spike/net_spike.gd` | P0 ④ 교실 네트워크 시험 화면 | ✅ |
| `core/net/hub_service.gd` | 서버 측 팀 허브: fetch/push 처리 (Git 코어의 허브 로직 재사용) | P1.5 |
| `scenes/teacher/` | 선생님 모드 화면 (방·팀·현황판) | P3 |
| 헤드리스 서버 실행 | `godot --headless --path game -- --server --port 8910` | P1.5 |

- `core/net`도 Node를 쓰지 않고 `poll()` 방식 → 헤드리스 테스트·서버 실행이 같은 코드.
- 인터넷 서버(A)는 리눅스에서 헤드리스 실행 + 앞단의 웹 서버(예: Caddy, nginx)가 TLS를 처리하는 구성을 권장.

## 9. 위험

| 위험 | 대응 |
|---|---|
| 교내망에서 PC끼리 통신 차단 | P0 ④ 탭으로 확인 → 인터넷 서버(A)로 전환 |
| 선생님 PC 방화벽 허용 불가 | 전산 담당에게 포트 8910 허용 요청, 또는 A 방식 |
| 서버가 수업 중 멈춤 | 학생 작업은 각자 PC에 있으므로 유실 없음. 서버 재시작 시 팀 허브는 선생님 PC에 자동 저장된 사본에서 복구 |
| 짝이 결석·지각 | NPC 대체 (2장 자동 대체 규칙) |
| 한 학생이 너무 빨라 짝이 따라오지 못함 | 역할 카드에 "기다리기" 단계, 먼저 끝나면 리뷰어 역할 |
| 장난 (일부러 충돌·방해) | 서버 차단 규칙 + 선생님 퇴장 + 모든 행동이 커밋 기록에 남음을 안내 (그것도 Git 교육) |
