# 🌐 협업(온라인) 설계서
### 「커밋 크래프트」 교실 협업 모드 v1.1 (2026-11-03 기획 점검 반영)

> **결정: 협업은 게임의 핵심이므로 온라인(네트워크) 협업을 MVP에 넣는다.**
> 혼자 하는 NPC 모드는 없애지 않고 **"네트워크가 안 될 때·짝이 없을 때"의 대체 수단**으로 남긴다.

## 1. 온라인 협업의 학습 목적과 구현 범위

**왜**: push 거절, pull 병합, 충돌, Pull Request 리뷰는 *다른 사람*이 있어야 의미가 생긴다. NPC는 각본대로만 움직이지만, 친구는 예상하지 못한 순간에 push하고, 같은 줄을 고치고, 리뷰에 이의를 단다. 그 경험이 협업 학습의 본체다.

**통신 빈도를 줄이는 근거**: Git은 원래 **실시간 동기화를 하지 않는다.** 각자 자기 컴퓨터에서 작업하고, `push`·`fetch`·`pull`을 하는 순간에만 서버와 통신한다.
→ 저장소 동기화는 요청·응답으로 제한한다. 다만 개인별 체험 판정, 단계 동기화, 재접속, NPC 대체, 서버 복구는 별도 작업이며 통신량이 적다는 이유로 일정에서 제외하지 않는다.

| 일반 온라인 게임 | 커밋 크래프트 |
|---|---|
| 초당 수십 번 상태 동기화 | `push`/`fetch`/PR 할 때만 통신 |
| 지연(렉)이 게임을 망침 | 0.5초 늦어도 문제없음 |
| 서버가 모든 상태를 관리 | 서버는 **허브 섬(원격 저장소)만** 관리, 각자 마을은 각자 PC에 |
| 연결이 끊기면 게임 중단 | 끊겨도 **커밋은 계속 가능** (push만 못 함 — 실제 Git과 같음) |

> 💡 **게임의 네트워크 구조 자체가 GitHub의 구조와 같다.** 서버 = GitHub, 학생 PC = 각자의 로컬 저장소. 구조가 곧 교재다.

```mermaid
flowchart LR
    subgraph 학생A PC
      A[내 마을<br/>로컬 저장소]
    end
    subgraph 학생B PC
      B[내 마을<br/>로컬 저장소]
    end
    subgraph 서버 = 허브 섬
      H[(팀 허브 저장소<br/>bare repo)]
    end
    A -- push / fetch --> H
    B -- push / fetch --> H
    H -. "알림: 단비가 push했어요" .-> A
```

## 2. 접속 방식 (공통 규약, 첫 시범은 한 방식 선정)

- 첫 시범 기본 후보는 **Windows exe + B 교실 서버 + 2인 팀**이다. 이는 검증 전 작업 가정이며 학교 실행 허용·교내망 통과를 의미하지 않는다.
- P0 결과로 배포 1종(exe/웹), 서버 1종(A/B), 운영 담당·주당 작업 시간·시범 일정을 기록하고 그 조합만 첫 시범 필수로 검증한다. 웹을 선택하면 A가 필요하다. C(NPC 대체)는 선택한 클라이언트에서 필수다.
- 선택하지 않은 배포·서버 조합과 3~4인 팀은 후속 지원이다. P0에서 선택 조합이 모두 실패하면 NPC 수업으로 전환하고 사람 간 협업 검증은 미완료로 보고한다.

| 방식 | 서버 위치 | 장점 | 단점 | 이런 학교에 |
|---|---|---|---|---|
| **A. 인터넷 서버** | 클라우드·교육청·학교 서버 (Godot 헤드리스) | 학교 방화벽 통과가 쉬움(`wss://`, 443 포트), 웹판도 접속 가능, 집에서도 이어서 가능 | 서버 운영 필요(소액), 개인정보 처리 검토 | 인터넷이 잘 되는 학교 |
| **B. 교실 서버** | 선생님 PC (게임의 "선생님 모드") | 인터넷 불필요, 데이터가 교실 밖으로 안 나감, 비용 0 | Windows 방화벽 허용 필요(관리자 권한), 교내망에서 PC끼리 통신이 막혀 있을 수 있음, 웹판은 접속 불가(exe 전용) | 인터넷이 막힌 학교 |
| **C. 혼자 모드 (NPC)** | 없음 | 언제나 동작 | 진짜 협업 아님 | 네트워크 실패·결석·자율학습 |

**자동 대체 규칙**
- 서버에 연결 못 하면 → "혼자 모드로 진행할까요?" (진도는 그대로 인정)
- 팀원이 퇴장하거나 접속 생존 신호가 3분 이상 끊기면 → NPC 대체 선택 제시. 단순 입력 대기는 제외하며 역할 인계·복귀는 4.1.1을 따른다
- 연결이 끊기면 → 작업은 계속, `push`/`fetch` 시 "허브 섬과 연결이 끊겼어요" (실제 Git의 네트워크 오류와 같은 경험)

**P0에서 확인할 것** → `game/` P0 스파이크 **④ 교실 네트워크** 탭 (작성됨)
1. 선생님 PC에서 서버 열기가 되는가 (방화벽 창, 관리자 권한 필요 여부)
2. 학생 PC 3대 이상이 선생님 PC 주소로 접속되는가
3. (가능하면) 인터넷 서버 주소로 접속되는가
→ 결과에 따라 학교별 기본 방식을 A 또는 B로 정한다.

## 3. 방과 팀

| 개념 | 설명 |
|---|---|
| **방(교실)** | 선생님이 만든다. 6자리 방 코드 (예: `K7Q-M2X`). 학생은 방 코드 + 닉네임으로 입장, **선생님 승인 후** 참여 |
| **팀** | 첫 시범은 **2명**. 선생님이 자동/수동 편성. 팀마다 허브 저장소 1개. 3~4인 운영은 후속 지원 |
| **역할 카드** | MVP는 작성자·받는 사람/해결자 2역을 스테이지 안에서 교대. 각자 자기 PC에서 필수 체험 수행. 리뷰어·메인테이너는 챕터 6 이후 |
| **학급 허브** | 이벤트용: 반 전체가 하나의 "학급 도시" 저장소에 PR (챕터 6 이후) |

### 3.1 수업 흐름 (선생님 화면)
1. 선생님 모드 실행 → 서버 시작 → **방 코드와 접속 주소**를 크게 표시 (프로젝터용)
2. 학생 입장 → 대기실 명단 → 승인 → 팀 편성 (자동: 출석 순서대로 2인 1팀)
3. 스테이지 시작 신호 → 모든 팀에 같은 스테이지 배포
4. **진행 현황판**: 팀별 허브 그래프·클리어 여부·막힌 팀 표시
5. 마무리: 프로젝터로 한 팀의 그래프를 띄워 함께 해석 ("여기서 왜 병합 커밋이 생겼을까?")
6. 수업 종료 → 진도 요약을 선생님 PC에 CSV로 저장 → 서버 데이터 삭제

## 4. 협업 스테이지 (챕터 5 협업판)

> **개인 완료 = 개인 로컬 상태 + 본인의 체험·퀴즈 조건. 팀 완료 = 공동 허브 목표 + 두 사람 모두 개인 완료.** 최종 파일이 같더라도 체험이 누락되면 개인 완료를 부여하지 않는다.
> 체험은 서버가 `student_id / stage_id / round_id / event`로 확인·중복 제거한다. `PushRejected`, `ConflictResolved` 등은 실제 명령 결과로만 발행한다. 참가자가 직접 보내는 준비 메시지로 학습 완료를 인증하지 않는다.
> NPC 모드도 같은 개인 학습 목표를 사용하고 모드만 별도로 기록한다. 아래 협업판은 NPC 트리거를 단순 치환하지 않고 라운드와 개인별 목표를 정의한다.

| 스테이지 | 혼자판 (NPC) | 협업판 (2인 팀) |
|---|---|---|
| 5-2 섬 복제 | 단비의 허브를 clone | **두 사람이 같은 팀 허브를 각자 clone** → 같은 마을이 두 PC에 생김 |
| 5-3 비행선 출발 | 커밋 후 "단비가 볼 수 있나?" 퀴즈 | A가 커밋 → 두 사람 예측 퀴즈 → push 전후 허브 비교. 역할을 바꿔 B도 commit·push하고 A도 관찰. 두 사람 모두 커밋≠업로드를 확인 |
| 5-4 망원경과 우편함 | 단비가 push, 플레이어 fetch | A가 push → B가 fetch하고 main·작업장 불변 확인. 역할을 바꾼 두 번째 고정 fixture에서도 A가 직접 fetch. 각자 퀴즈·fetch 체험을 충족 |
| 5-5 우편함 열기 | merge origin/main, pull | 각자 동등한 초기 fixture에서 `merge origin/main` 후 새 원격 변경에 `pull` 수행. 두 사람 모두 MergeFastForward·Pulled 체험 및 main=hub 확인 |
| 5-6 착륙 거부! | 각본으로 거절 재현 | 공통 기준에서 서로 다른 파일 커밋 → 두 사람 준비 확인 → A 먼저 push, B 거절·pull·push → 역할을 바꿔 두 번째 라운드. 각자 거절 1회 이상 (4.1) |
| 5-7 연결선 | 혼자 진행 | 혼자 진행 (협업 불필요) |
| 5-B 두 섬의 경주 | 각본 충돌 | 같은 기준 커밋에서 분수 장식을 서로 다르게 커밋 → 준비 확인 → 지정 순서 push·거절·pull 충돌 → 합의·해결. 두 번째 라운드에는 해결자를 바꾼다 (4.3) |

### 4.0 5-3~5-5: 발신·수신 역할과 개인별 기록
- 공통: 각 라운드 fixture는 교사가 시작하는 수업 초기화이며 실제 Git 명령이나 학생의 reset으로 표시하지 않는다. 시작 시 기준 커밋·역할을 보여주고 앞 라운드 체험 기록을 보존한다. 학생별 완료 조건은 자신이 수신/발신한 라운드의 상태와 이벤트로 검사한다.
- **5-3**: 공통 clean 기준에서 A가 건설·add·commit → 두 사람 퀴즈 → A push → B가 허브 화면 비교 후 pull. 이어 B가 다른 파일로 같은 절차를 수행하고 A가 pull. 각자 직접 커밋·push·퀴즈를 완료하고 최종 main=hub·clean. ★★ 개인당 add·commit·push·pull **4개 이하**.
- **5-4**: 라운드 1은 A에게 미전송 커밋 2개, B에게 이전 main 및 이전 origin/main을 제공한다. A push 후 B status→fetch→status·퀴즈로 수신 라운드의 main/작업장 불변과 origin/main=hub를 확인한다. 라운드 2는 역할을 바꾼 독립 fixture로 A도 같은 수신 경험을 한다. 각자의 완료는 본인의 수신 라운드 불변 상태·퀴즈·fetch 기록으로 판정하며 발신 라운드의 main을 과거 값으로 되돌리라고 요구하지 않는다. ★★ 개인당 push·fetch **2개 이하**.
- **5-5**: 라운드 1 fixture는 허브·A main에 정류장 커밋, B origin/main에도 해당 커밋, B main은 이전 커밋이다. B가 merge origin/main하면 A의 조명 미션 카드를 열어 A add·commit·push → B pull. 두 사람 main=hub·clean 후 역할을 바꾼 독립 fixture에서 반복한다. 개인별 수신 라운드 MergeFastForward·Pulled와 최종 동기화 확인. ★★ 개인당 수신 merge·pull 2개 + 발신 add·commit·push 3개 = **5개 이하**. 발신자의 초기 작업장은 clean이며 수신 merge 확인 뒤 조명을 직접 수정·add한다. 자동 add로 실제 동작을 숨기지 않는다.
- NPC판의 개인 목표를 그대로 동시에 적용하지 않는다. 특히 5-4의 main 불변은 개인의 수신 라운드에서만 판정한다. 팀 완료는 두 학생 각각의 체험과 각 라운드 공유 목표를 충족해야 한다.

### 4.1 5-6: 개인별 push 거절 체험 보장
1. 라운드 시작 시 두 학생 모두 로컬 main=hub main, 작업장 clean임을 확인한다. 각각 다른 파일을 수정·add·commit하고 준비 버튼을 누른다. 서버는 제출 객체와 부모 관계로 두 tip이 같은 기준에서 갈라졌음을 검사한다.
2. 둘 다 준비되기 전에는 수업 안내에서 push 단계로 진행하지 않는다. 라운드 1의 첫 push 담당은 A, 거절·복구 담당은 B다. A의 성공을 확인한 뒤 B가 직접 push → 실제 거절 → pull → push한다. A도 pull하여 둘 다 clean 및 main=hub가 되어야 라운드가 끝난다.
3. 라운드 2는 라운드 1의 동기화된 결과를 기준으로 새 변경을 만들고 순서를 바꾼다(B 성공 → A 거절·pull·push → B pull). 안내를 벗어난 선행 fetch/pull로 갈라짐이 없어졌다면 완료 이벤트를 만들지 않고 준비 단계를 다시 구성한다. 교사에게 재준비 사유를 보여준다.
4. **개인 목표**: 본인의 `PushRejected` 1회 이상 + 본인이 만든 커밋의 허브 도달 + 본인 main=hub 및 clean. **팀 목표**: 두 라운드 변경 전부 보존 + 두 사람 개인 완료. 먼저 성공한 학생에게 거절 체험을 자동 인정하지 않는다.
5. **★★**: 개인당 두 라운드 합계 상태 변경 성공 명령 **8개 이하**, force 시도 없음. 정상 경로는 라운드당 add·commit·성공 push·pull 각 1회이며 거절 push·조회·재전송은 제외한다.

**실제 Git 규칙 유지**: push 가능 여부는 시뮬레이터 명세 4.18의 조상 관계와 객체 보유 여부로 판단한다. 참조 갱신에는 비교 후 교체로 경쟁을 막되, 교육 단계 미충족을 Git 오류로 위장하지 않는다. 준비·순서 안내는 수업 UI에서 표시하며 실제 거절은 실제 분기 상태에서만 발생한다.

### 4.1.1 중단·재접속·NPC 대체
- 준비·체험·완료 기록은 라운드 식별자로 중복 제거하고 실제 서버 처리 결과를 기준으로 복원한다. 응답이 유실된 push는 허브 tip을 확인한 뒤 재시도하며 학습 이벤트를 중복 발행하지 않는다.
- 입력이 3분 없다는 이유만으로 NPC로 바꾸지 않는다. 접속 생존 신호가 끊기거나 퇴장한 경우 교사/남은 학생에게 대체 선택을 제시한다. 수업 중 사고 시간을 부재로 판단하지 않는다.
- NPC 전환은 기존 인간 세션을 중지하고 서버가 소유하는 단일 NPC 참가자로 역할을 교체한다. 이미 성공한 push는 보존하며 미완료 준비 단계만 재구성한다. 돌아온 학생은 현재 라운드가 끝난 뒤 합류한다. 같은 역할을 사람과 NPC가 동시에 수행할 수 없다.
- 역할 대체 NPC는 시뮬레이터 명세 5.2의 별도 모드를 사용한다. 담당 역할의 의도된 거절·충돌·복구는 허용하며 단독 NPC의 무충돌 각본 규칙을 적용하지 않는다. 대체 NPC가 완료한 체험은 이탈한 학생에게 귀속하지 않는다.
- 서버 자체에 접속할 수 없으면 마지막 확인된 로컬 상태를 보존하고 독립 NPC fixture에서 미완료 체험을 수행한다. 서버에 반영되지 않은 내용을 팀 완료로 기록하지 않으며 친구 모드와 NPC 모드를 따로 남긴다.

### 4.2 챕터 6 (PR·리뷰) — 2차 범위, 온라인 전제
- Pull Request, 코드 리뷰, 승인/변경 요청은 **진짜 사람끼리 해야 의미가 있다** → 2차에서 온라인 모드를 전제로 설계.
- 리뷰 코멘트는 프리셋 문장 + 금칙어 필터를 거친 짧은 자유 입력.

---

### 4.3 5-B: 두 학생 모두 충돌 해결
- 라운드 1: main=hub의 공통 기준에서 A는 분수 장식=꽃, B는 장식=등불로 각각 커밋한다. 두 tip의 기준·서로 다른 같은 줄 변경을 확인한 뒤 A push → B push 거절 → B pull 충돌 순서로 진행한다. A의 push 후 B가 새로 수정하는 방식은 허용하지 않고 준비 단계를 다시 연다.
- B는 프리셋 대화로 합의한 `꽃, 등불`을 직접 편집·add·commit·push한다. A도 pull하고 서로의 변경 보존을 확인한다. 두 tip이 같은 기준의 다른 장식 값을 담아야 실제 Git 병합에서 충돌이 생긴다.
- 라운드 2: 동기화된 새 기준에서 A는 `꽃, 등불, 리본`, B는 `꽃, 등불, 별`로 같은 장식 줄을 다시 수정·커밋한다. B 먼저 push, A가 거절·pull 충돌을 겪고 합의 결과 `꽃, 등불, 리본, 별`로 직접 해결한다. 기존 꽃·등불은 유지한다.
- **개인 목표**: 본인 PushRejected + 본인 병합 충돌 발생 + 본인 편집 후 해결 커밋(부모 2개, 표시자 없음) + 본인 퀴즈(무엇을 보존했는가) + main=hub 및 clean. 관찰·대화만으로 해결 체험을 인정하지 않는다.
- **팀 목표**: 두 사람 개인 완료 + 허브에 두 사람 변경과 두 해결 커밋 보존 + 최종 장식에 꽃·등불·리본·별 모두 포함. NPC판의 플레이어 3커밋·단비 2커밋 조건은 이 협업판에 적용하지 않는다.
- **★★**: 개인당 두 라운드 합계 상태 변경 성공 명령 12개 이하, force 없음. 모범 경로는 먼저 push하는 라운드 4개, 직접 해결하는 라운드 6개로 개인당 10개이며 조회·거절은 제외한다.
- 준비 전 이른 push, 이른 fetch/pull, 상대 이탈, 해결 중 재접속, 중복 준비 통지를 각각 검증한다. 체험이 성립하지 않으면 해당 라운드를 재준비하며 Git 규칙을 바꾸어 충돌을 강제로 만들지 않는다.

## 5. 통신 규약

- 전송: **WebSocket**, 메시지 = JSON 1개 (`"t"` = 종류). 교실 서버 `ws://<선생님PC>:8910`, 인터넷 서버 `wss://<주소>`.
- Godot 고수준 멀티플레이(RPC·동기화)는 쓰지 않는다: 실시간 동기화가 필요 없고, exe·웹판 공통의 단순 JSON이 디버깅과 학교망 문제 진단에 쉽다.
- 서버는 같은 Godot 프로젝트를 **헤드리스로 실행**한다 → 허브 판정(push 거절 등)에 클라이언트와 **같은 Git 코어 코드**를 쓴다.

| 방향 | 메시지 | 내용 | 상태 |
|---|---|---|---|
| → 서버 | `hello` | 버전, 닉네임, 방 코드 | ✅ 스파이크 |
| ← | `welcome` / `error` | 내 id, 명단 / 버전 불일치 등 | ✅ |
| ← | `joined` / `left` | 명단 변경 | ✅ |
| → / ← | `say` / `said` | 프리셋 알림 문장 | ✅ (시험판은 짧은 문장) |
| → | `fetch` | 팀 허브 id, 내가 가진 커밋 목록 | P1.5 |
| ← | `pack` | 내가 없는 객체(커밋·파일), 허브 브랜치 위치 | P1.5 |
| → | `push` | 브랜치별 `{old, new}`, 새 객체 | P1.5 |
| ← | `push_result` | 성공 / `rejected: fetch-first \| non-fast-forward` | P1.5 |
| ← | `activity` | "단비가 main에 push했어요" (**알림만**, 내 저장소는 fetch 전까지 그대로) | P1.5 |
| → / ← | `stage_ready` / `stage_phase` | 학생·스테이지·라운드, 준비 tip·기준, 담당 역할·단계. 객체·참조·실제 이벤트를 서버에서 검증, 중복 제거 | P1.5 |
| → / ← | `teacher_*` | 방 잠금, 승인, 팀 편성, 스테이지 시작·초기화, 현황 조회 | P3 |
| → / ← | `pr_*` | PR 생성·리뷰·병합 | 2차 |

**크기·빈도 제한**: 메시지 256KB, 학생당 초당 5개. 저장소가 작아(커밋 수십 개, 텍스트 파일 수십 개) 충분하다.
